# Follow along: Claude Code Fixes a Real Open-Source Bug (episode 2)

Every prompt is exactly what is typed in the video (*Code & Agents*, "From Java Developer to AI Engineer",
part 2). Your agent will not do exactly what mine did: that's normal, and the check at the end of each step
is how you tell whether it worked. The agent's own commits: `a2b52a7` (step 2) and `a9adaf1` (step 5) on
branch `ep02-real-bug`, tag `ep02-final`.

## What you need

- [Claude Code](https://code.claude.com/docs/en/quickstart) on a Pro plan, or with an API key (the video: Sonnet 5.5).


- PetClinic running, without Docker. Build once, then start config-server and discovery-server first, then the
  others, each in its own terminal (genai-service isn't needed):

```bash

```

  Ready when `http://localhost:8761` lists CUSTOMERS-SERVICE, VETS-SERVICE, VISITS-SERVICE and API-GATEWAY,
  and `http://localhost:8080` shows the app. The data is in memory: restarting a service resets it.
- Then run `claude` in the repo folder.

The bug: [spring-petclinic-microservices#558](https://github.com/spring-petclinic/spring-petclinic-microservices/issues/558),
"Backend accepts pet birth dates in the future".

## Step 1. Reproduce the bug

Paste (it's one prompt; check that the whole text arrived before you press Enter):

```
The services are running locally (API gateway on port 8080). Reproduce this bug report against the running app, without changing any code yet:

Bug: customers-service lets you create or update a pet with a birth date in the future. Creating a pet (POST /owners/{ownerId}/pets) or updating one (PUT /owners/{ownerId}/pets/{petId}) with a birthDate like 2030-01-01 succeeds. It should be rejected with 400 Bad Request.
```

**Look for:** real requests through the gateway, a control with a past date, and the cause: no constraint on
`birthDate`, and **no `@Valid` on either handler** (`PetResource.processCreationForm` and `processUpdateForm`).

Check it yourself:

```bash
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/api/customer/owners/1/pets \
  -H 'Content-Type: application/json' \
  -d '{"id":0,"name":"FuturePet","birthDate":"2030-01-01","typeId":2}'
curl -s localhost:8080/api/customer/owners/1/pets/14     # use the id your POST returned
```

**Look for:** `HTTP 201`, and a read-back `birthDate` of `2029-12-31T...`: a day early, a second bug (in ahead-
of-UTC time zones; the agent finds it in step 4).

## Step 2. Fix it, test first

```
Fix it. Write a failing test first, then make it pass, then run the customers-service tests.
```

**Look for:** the new tests run *before* the fix and fail with the bug's symptoms (`expected:<400> but was:<201>`,
`<204>` for the update); then `@PastOrPresent` on `PetRequest.birthDate` and `@Valid` on both handlers.

Check it yourself:

```bash
./mvnw -B test -pl spring-petclinic-customers-service 2>&1 | grep -E "Tests run:|BUILD"
```

**Look for:** `Tests run: 4, Failures: 0` (with the agent's two new tests) and `BUILD SUCCESS`. The agent's
version is commit `a2b52a7` on branch `ep02-real-bug`.

## Step 3. Prove it on the running app

```
Restart customers-service with your fix and show that the same request is now rejected.
```

**Look for:** it stops only customers-service, rebuilds and starts it, and replays the requests.

Check it yourself (after customers-service has restarted with the fix):

```bash
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/api/customer/owners/1/pets \
  -H 'Content-Type: application/json' \
  -d '{"id":0,"name":"FuturePet","birthDate":"2030-01-01","typeId":2}'
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/api/customer/owners/1/pets \
  -H 'Content-Type: application/json' \
  -d '{"id":0,"name":"PastPet","birthDate":"2020-01-01","typeId":2}'
```

**Look for:** `HTTP 400`, then `HTTP 201`. If you get `405` (or `500`) right after a restart, a killed instance is
still registered in Eureka and the gateway sends some calls to it: wait a couple of minutes and try again.

## Step 4. Ask for a code review

```
Review the whole PetResource class the way a senior engineer reviews a pull request. List anything else you would flag, most serious first. Don't change any code yet.
```

**Look for:** the update ignoring the URL (it uses the body's `id`), an unknown `typeId` being ignored, birth
dates returned a day early, and the time-zone edge of `@PastOrPresent` itself.

Check finding #1 yourself (before step 5's fix):

```bash
curl -s localhost:8080/api/customer/owners/1/pets/1
curl -s -w 'HTTP %{http_code}\n' -X PUT localhost:8080/api/customer/owners/6/pets/7 \
  -H 'Content-Type: application/json' \
  -d '{"id":1,"name":"Hijacked","birthDate":"2010-09-07","typeId":1}'
curl -s localhost:8080/api/customer/owners/1/pets/1
```

**Look for:** Leo (owner 1's cat), then `HTTP 204` for a request addressed to owner 6's pet 7, then Leo renamed
"Hijacked".

Check finding #2 yourself:

```bash
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/api/customer/owners/1/pets \
  -H 'Content-Type: application/json' \
  -d '{"id":0,"name":"Typeless","birthDate":"2020-01-01","typeId":999}'
```

**Look for:** `HTTP 500`, not the 201 the agent predicted: `pets.type_id` is `NOT NULL` in the database, and a
unit test with a mocked repository can't show that.

## The flaw it flagged: test it yourself

The birth date is read as midnight UTC and compared with the current moment. So "today" in a time zone ahead of
UTC is in the future for a few hours: in New Zealand every day until 13:00, in India until 05:30. Try it when
your local date is ahead of the UTC date (`date -u` shows the UTC date), with your local date:

```bash
curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/api/customer/owners/1/pets \
  -H 'Content-Type: application/json' \
  -d '{"id":0,"name":"Puppy","birthDate":"YYYY-MM-DD","typeId":2}'    # your local date
```

**Look for:** `HTTP 400` for a pet born today. The upstream pull request (#559) has the same edge. Episode 3 turns
the fix into a decision written in a spec: whose "today" counts.
