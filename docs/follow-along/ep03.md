# Follow along: Spec-Driven Development with Claude Code (episode 3)

Every prompt is exactly what is typed in the video (*Code & Agents*, "From Java Developer to AI Engineer",
part 3). Your agent will not do exactly what mine did: that's normal, and the checks in each step are how you
tell. The agent's own commit: `d383e42` on branch `ep03-upcoming-visits`, tag `ep03-final` (pull request #1 on
this fork).

## What you need

- Java 17 or newer (the video ran on Java 25), and a terminal that can run `./mvnw` (Git Bash or WSL on Windows).
- [Claude Code](https://code.claude.com/docs/en/quickstart) on a Pro plan, or with an API key.
- The repo, at the start tag:

```bash
git clone https://github.com/codeandagents/spring-petclinic-microservices
cd spring-petclinic-microservices
git checkout ep03-start        # the spec and nine failing acceptance tests
```

## Step 1. Read the spec, see the red tests

Open `docs/specs/upcoming-visits.md`, then `UpcomingVisitsAcceptanceTest` in `spring-petclinic-visits-service`.
Run the tests (about two minutes):

```bash
./mvnw -B test -pl spring-petclinic-visits-service -Dtest=UpcomingVisitsAcceptanceTest
```

**Look for:** `Tests run: 9, Failures: 9`. Seven say `Status expected ... but was:<404>` and one finds no `items`
(no endpoint yet). One says `expected:<2026-10-21> but was:<2026-10-20>`: the visit-date bug from episode 1,
reproduced on any machine.

## Step 2. Plan it

In the repo, run `claude`, choose Sonnet 5.5 with `/model`, then press **Shift+Tab** until the bottom line says
**plan mode**. Paste:

```
Implement the spec in docs/specs/upcoming-visits.md. Its acceptance tests are already in the repo, and they fail.
```

**Look for:** a plan that touches visits-service (date fix, `Clock`, endpoint), api-gateway (one call to
customers-service, DTOs, endpoint) and the AngularJS page. Read it against the spec. Approve it as it is.

## Step 3. Build it

Choose **Yes, and use auto mode**. Expect 10-20 minutes. When it's done, run the same command as in step 1:

```bash
./mvnw -B test -pl spring-petclinic-visits-service -Dtest=UpcomingVisitsAcceptanceTest
```

**Look for:** `Tests run: 9, Failures: 0`, `BUILD SUCCESS`. Then read its summary for the choices it made where
the spec was silent.

## Step 4. Check it against the spec

```
Run the build the spec asks for. Then go through the spec rule by rule and show me where the code meets each one.
```

**Look for:** a green `./mvnw test -pl '!spring-petclinic-genai-service'`, and a `file:line` for each of R1-R4.
Open those lines yourself: R1 in `VisitResource.upcoming`, R2 in `Visit.date` (a `LocalDate`), R3/R4 in the
repository call. It should also name its own gaps.

## Step 5. Prove it live

Start PetClinic first (`./scripts/run_all.sh` or each service with `./mvnw spring-boot:run`, genai-service not
needed), then:

```
PetClinic is running on this machine from the jars in this repo, with the API gateway on port 8080. Restart the services you changed, add three visits for the next few days through the API, and show me what the new gateway endpoint returns.
```

Check it yourself (Git Bash; dates are relative to today, in UTC like the app's default clinic zone):

```bash
for n in 1 3 5; do curl -s -X POST localhost:8080/api/visit/owners/1/pets/1/visits \
  -H "Content-Type: application/json" \
  -d "{\"date\":\"$(date -u -d "+$n day" +%F)\",\"description\":\"checkup in $n days\"}"; echo; done
curl -s localhost:8080/api/gateway/visits/upcoming
curl -s -o /dev/null -w "HTTP %{http_code}\n" "localhost:8080/api/gateway/visits/upcoming?days=0"
```

**Look for:** three items in date order with `petName` and `ownerName`, and `HTTP 400` for `days=0`.
If you get a `500` straight after a restart, a dead service instance is still registered in Eureka: wait about
90 seconds, or remove it in the Eureka dashboard (`localhost:8761`). Then open `http://localhost:8080`, reload,
and click **Upcoming visits**.

## Step 6. Open the pull request

```
Commit the work on this branch, push it, and open a pull request on our fork, codeandagents/spring-petclinic-microservices, into the branch ep02-real-bug.
```

Use your own fork and branch names. **Look for:** the pull request on *your* fork, not on the upstream project
(the `gh` command should name the repository), and a description that says what was and wasn't checked.
